Projects with uv

Why does code work on my laptop and fail on yours? Often the libraries differ by a small version. A project solves this the way a recipe card does:

  • pyproject.toml is the ingredient list: our libraries and the Python version, with ranges such as httpx>=0.28.
  • uv.lock is the recipe card: the exact version of every library, with checksums.
  • .venv, the virtual environment, is the kitchen where the dish gets cooked.

The tool uv reads the recipe card and builds the same kitchen on any machine with uv sync.

Now, we'll watch uv add two libraries to a fresh project:

$ uv add httpx pydantic
Resolved 12 packages in 316ms
Installed 11 packages in 12ms
 + httpx==0.28.1
 + pydantic==2.14.3
 ...

We asked for two libraries and uv installed eleven, because libraries stand on libraries. Commit both files to Git, and anyone who clones the repository runs uv sync to get the same kitchen.

Type Hints and Pydantic

A type hint says what a function expects and what it returns:

def total(prompt_tokens: int, completion_tokens: int) -> int:
    return prompt_tokens + completion_tokens

A token is a small piece of text that a language model reads or writes, and providers count tokens to measure usage and cost. Hints help readers and checkers such as mypy, but at runtime Python treats them as notes, so a provider that sends "twelve" where a number belongs breaks the program far from the cause. For data that arrives from outside, we want a guard, and that guard is Pydantic.

Our picture is a customs desk: the officer opens each parcel, checks it against the rules and only then lets it through.

We describe a parcel once, as a class. Here Usage holds two whole numbers that must be zero or higher:

class Usage(BaseModel):
    prompt_tokens: int = Field(ge=0)
    completion_tokens: int = Field(ge=0)

If a reply says prompt_tokens is 5 and completion_tokens is 7, both pass and the total is 5 + 7 = 12. If completion_tokens were -3, the officer would stop the parcel and name the field and the reason. Real output from our demo shows a broken parcel with three problems, all reported together:

rejected with 3 problems:
  text                       String should have at least 1 character
  usage.prompt_tokens        Input should be greater than or equal to 0
  usage.completion_tokens    Input should be a valid integer, unable to parse string ...

By default Pydantic works in lax mode, where the text "5" becomes the number 5, and strict mode asks for exact types. Put a customs desk at every border where data enters: the incoming request, the provider's reply and the settings file. Inside the service, functions can trust the types.

Async Python

Why does a model call take three seconds? Mostly because our program is waiting while the provider's computer works. That waiting is I/O, and such a program is I/O-bound.

Picture a restaurant with three tables and one waiter. A synchronous waiter takes an order, stands in the kitchen until the dish is ready, and only then visits table two: nine minutes at the last table. An asynchronous waiter hands each order to the kitchen and moves on, so all three dishes cook at once and the last table waits three minutes.

Python has this waiter built in, called the event loop, and it runs in a single thread. A function declared with async def creates a coroutine when called, a recipe for work that the loop can run. The word await marks a point where the function says: I am waiting, so serve someone else, and resume me when my result is ready.

Two rules keep you safe. First, await works inside an async function. Second, put await in front of every coroutine call you want to run, because a bare call only creates the coroutine and Python prints a warning that names it. Start a whole program with asyncio.run, once, at the top.

Inside the loop there is a ready list and a waiting list. Each task runs until its await, then moves to the waiting list, and when its reply arrives it returns to the ready list. A blocking call such as time.sleep holds the thread and freezes every task, so waiting always uses await.

To run many coroutines together we use asyncio.gather. It starts them all, waits until every one has finished and returns the results in input order. One after another, 3 + 3 + 3 = 9 seconds. All at once, the slowest call decides the total, max(3, 3, 3) = 3 seconds. This is concurrency, many tasks making progress during overlapping time, and it suits I/O-bound work such as model calls.

Our command line confirms it with real output, and the --sequential flag takes 9.04 seconds for the same question:

$ uv run python -m caredesk_fanout.cli Summarise this referral alpha beta gamma
alpha     3.02 s   15 tokens  [alpha] The discharge summary is complete ...
wall-clock time: 3.03 s

What about a hundred providers? Starting everything at once can overload our computer or hit a provider's rate limit, so we limit the calls in flight, like a door host who lets five of ten guests inside at a time. In Python, the door host is a semaphore. Ten calls of three seconds with a limit of five make two rounds, 6 seconds in total, compared with 30 one by one.

sem = asyncio.Semaphore(max_concurrency)   # the door host: lets N in at a time
async with sem:                            # wait here when too many calls are in flight
    response = await client.post(...)

Two more traps: forgetting await, and creating a new client for every call instead of sharing one.

Reliable Clients

Real networks sometimes fail with a timeout, a server error such as 503 or a rate limit, 429. Three rules cover most needs:

  1. Every call gets a timeout. Our client gives each call ten seconds, so a stuck call frees its place at the door.
  2. Retry what is temporary. Timeouts, connection errors and the codes 408, 429, 500, 502, 503 and 504 deserve another try, while a 400, 401 or 404 fails the same way next time and is reported at once.
  3. Stop after a few tries. Three extra attempts, then a failure result for that provider, while the others still deliver.

How long should we wait between tries? Exponential backoff doubles the wait each time, up to a cap: wait = min(cap, base × 2^attempt). With base 1 and cap 30, the waits are 1, 2, 4, 8, 16 and then 30 seconds. A thousand clients that failed together and wait exactly four seconds would all retry at the same instant, a thundering herd. Jitter, a random extra of up to half the wait, spreads those requests over two seconds, roughly 500 per second.

wait = min(policy.cap_s, policy.base_s * 2**attempt)
return wait + rng.uniform(0, wait * policy.jitter)

In the real demo, a flaky provider fails twice with a 503 and then answers, and each log line names the provider, the attempt, the reason and the wait:

91 ms  flaky: attempt 1 failed (HTTP 503); retrying in 0.29 s
386 ms flaky: attempt 2 failed (HTTP 503); retrying in 0.54 s
success after 0.86 s

Retries bring a new danger. Our client asks a billing service to charge a fee, the card is charged, the reply gets lost, and the client retries. The server sees a brand-new request, and the patient pays twice.

The fix is an idempotency key. Idempotent means that doing something twice has the same effect as doing it once.

The client creates a random unique key before the first attempt and sends it in a header, and the server remembers each key with its reply, so a retry receives the saved reply. We measured it with a mock billing provider: without a key, work done 2× and charged 2×; with a key, work done 1× and charged 1×.

key = new_idempotency_key() if use_idempotency else None   # created once, outside the retry loop
headers = {"Idempotency-Key": key} if key else {}          # sent on every attempt

Testing, Logging and Settings

A pytest test is a function whose name starts with test, with assert statements that say what must be true. Our lab has twenty-one tests, and they pass in 1.13 seconds. To test network code offline, we replace the network with HTTPX's built-in mock transport: a small function plays the provider, answers instantly and can misbehave on purpose. One test proves that concurrency pays off:

assert fast.wall_s < 0.45    # about 0.2 s: all at once
assert slow.wall_s >= 0.6    # about 0.6 s: one after another

Model text varies from run to run, so exact matches fail at random. Three techniques help: a contract tests what must always hold, such as every provider being accounted for; a property check tries many random cases, and two thousand seeds confirm every jittered delay lies between the wait and one and a half times the wait; a snapshot saves the shape of a result without wording or timing.

Three small habits finish the foundation. Use logging instead of print, so a setting can raise or lower the detail. Read settings with pydantic-settings from CAREDESK_ environment variables, the customs desk again, so a concurrency of zero stops start-up with a clear message. And add a small argparse command line. Keep secrets out of Git.

A SQL Refresher

Many AI applications store data in a relational database, and SQL is the language for asking questions. A table is a grid of rows (records) and columns (fields). Our lab has two tables of synthetic data, departments and appointments, and the question is which department keeps patients waiting the longest. We answer it with a join, a GROUP BY and a window function in SQLite, which ships with Python.

A join connects rows through a shared value: for each appointment, find the department whose id matches and put its name beside it.

SELECT a.id, d.name AS department, a.patient_code, a.wait_minutes
FROM appointments AS a
JOIN departments AS d ON d.id = a.department_id
WHERE a.id <= 6
ORDER BY a.id;

The result shows six rows: four Emergency rows with waits of 35, 50, 20 and 65 minutes, and two Cardiology rows.

A GROUP BY collapses rows that share a value into one row per group, and aggregate functions summarise each group. Emergency has four waits: 35 + 50 + 20 + 65 = 170, and 170 / 4 = 42.5 minutes on average, with 65 the longest. Cardiology averages 70 / 3 = 23.3 and Radiology 125 / 5 = 25.0, so sorted by average wait, Emergency comes first.

SELECT d.name AS department, COUNT(*) AS appointments,
       ROUND(AVG(a.wait_minutes), 1) AS avg_wait, MAX(a.wait_minutes) AS longest_wait
FROM appointments AS a
JOIN departments AS d ON d.id = a.department_id
GROUP BY d.name
ORDER BY avg_wait DESC;

A window function keeps every row and adds a column calculated over a window of related rows. For Radiology, RANK() OVER (PARTITION BY ... ORDER BY wait_minutes DESC) ranks the waits 40, 30, 25, 20 and 10 from 1 to 5, and a running average over the time order gives 40, 25, 23.3, 25 and 25. Window functions power rankings and moving averages.

Putting It All Together

The fan_out function creates the door host, opens one shared async client and builds one fetch_one coroutine per provider, and gather starts them all. Inside fetch_one, the key is created once, call_with_retries retries temporary failures, and model_validate_json is the customs desk. Any trouble becomes a failure result, so one bad provider leaves the others untouched, and a test proves it.

Here is a challenge for your own lab: twelve providers, three seconds each, and a door host that lets four in at a time. How long does the fan-out take? Twelve calls with four places make 12 / 4 = 3 rounds, and 3 × 3 = 9 seconds, compared with 36 seconds one by one. Then run the demos and the tests, add a fourth provider with a limit of two and predict the time, and make the flaky provider fail five times to watch the retry give up. The README of the part folder lists the commands.

To recap with our pictures: a recipe card makes a project reproducible, a customs desk checks data, one waiter serving many tables turns nine seconds into three, a door host limits who is inside, backoff with jitter and an idempotency key make retries safe, and tests prove it.

Why Python Engineering Comes First

Three Calls, Nine Seconds or Three

Imagine our hospital copilot needs second opinions from three different model providers. Each call takes about three seconds. If we ask them one after another, we wait nine seconds. If we ask all three at the same time, we wait three. The same work finishes in a third of the time.

We measured exactly that on a Mac, with three local stand-in providers that each take three seconds. One after another took 9.11 seconds. All at once took 3.02 seconds.

The difference comes from one idea, called async programming. By the end of this article, we will have turned that idea into a real program: a small, typed, concurrent, retried and tested client.

What We Build

The CareDesk fan-out client has a simple job. It takes one question, sends it to every provider at once, checks every reply and returns the answers together with any failures and the wall-clock time. Each habit in this lesson earns its place in that code, and the sections below add them one at a time.

Projects with uv

Why Code Works on One Laptop and Fails on Another

Let's start with a question every programmer meets: why does my code work on my laptop and fail on yours? Very often the answer is the libraries. One laptop has one version of a library, another has a different one, and a small difference can change behaviour.

The Recipe Card

Think of a recipe card. A list of ingredients such as flour and eggs leaves room for interpretation, while a card with exact brands, exact weights and exact steps lets any kitchen cook the same dish. In Python, two files play these roles:

  • pyproject.toml is the ingredient list. It names our libraries and the Python version we need, with ranges such as httpx>=0.28.
  • uv.lock is the recipe card. It records the exact version of every library, with checksums, including the libraries our libraries depend on.

The virtual environment, a folder called .venv, is the kitchen where everything gets cooked.

The tool uv is a fast project manager for Python. When a teammate runs uv sync, uv reads the recipe card and builds the same kitchen on their machine, with the same versions every time. That is what makes a project reproducible.

uv in Action

Let's watch uv build a project from an empty folder and read what it prints. First, uv init with a project name creates a project folder with a starter program, a pyproject.toml file and a readme.

Type Hints and Pydantic

Type Hints Are Labels

Next, type hints. When we read a function, how do we know what it expects and what it returns? A type hint answers right in the code:

def total(prompt_tokens: int, completion_tokens: int) -> int:
    return prompt_tokens + completion_tokens

Here total takes two whole numbers and returns a whole number. A token is a small piece of text that a language model reads or writes, and providers count tokens to measure usage and cost.

Type hints work like labels on boxes in a storeroom. They help the people who read the code, and they help tools: the editor can underline a mistake before we run anything, and a checker such as mypy can scan the whole project.

There is one catch. At runtime, Python treats these labels as notes for humans and tools. If a provider sends the text "twelve" where a number belongs, Python carries on until something breaks far from the real cause. For data from outside our program, we want a guard that checks the contents of the box. That guard is Pydantic.

Pydantic as a Customs Desk

How do we trust data that comes from outside our service, such as a provider's reply, a user's request or a settings file? Our picture is a customs desk at a country's border. Parcels arrive with a label that says what is inside. The officer opens each parcel, checks it against the rules, and only then lets it through.

Pydantic is that officer. We describe a parcel once, as a class. Usage has two whole numbers, prompt tokens and completion tokens, and both must be zero or higher. Pydantic checks every field the moment the object is built. A good parcel becomes a typed Python object. A broken parcel is stopped at the border, with a report of every problem found.

A tiny example with numbers. A reply says prompt_tokens is 5 and completion_tokens is 7. Both are whole numbers of at least zero, so the parcel passes, and the total is 5 + 7 = 12. If completion_tokens had been -3, the officer would stop the parcel and say which field and why.

The mechanism has a proper name. A Pydantic model is a class that inherits from BaseModel. Each field has a type, and Field can add rules, such as ge=0 (greater than or equal to zero) or min_length=1. Calling model_validate_json on raw bytes parses and checks in one step, with a checking engine written in Rust.

Seeing the Officer Work

Let's watch the officer with real output from our demo. The good parcel, with five prompt tokens and seven completion tokens, is accepted with a total of twelve. Now a broken parcel with three problems at once:

$ uv run python demos/02_validation.py
--- a good parcel
accepted: total tokens = 12, prompt_tokens = 5
--- a broken parcel
rejected with 3 problems:
  text                       String should have at least 1 character
  usage.prompt_tokens        Input should be greater than or equal to 0
  usage.completion_tokens    Input should be a valid integer, unable to parse string as an integer
--- a parcel with "5" where 5 is expected
accepted: total tokens = 12, prompt_tokens = 5

The text is empty, the prompt token count is -3, and the completion token count is the word twelve, spelled with letters. Pydantic lists all three problems together, so a developer can repair everything in one pass.

The last case is a surprise worth knowing about. A parcel arrives with the prompt token count written as the text "5", in quotes. By default, Pydantic works in lax mode, so it converts the text to the whole number 5 and accepts the parcel. Lax mode is friendly to real-world JSON, where numbers sometimes arrive as text. When a field needs exact types, Pydantic also offers strict mode.

Our Models in Code

Now, we'll define the shapes that cross the borders of our service in models.py:

class ChatRequest(BaseModel):
    """The question we send to a provider."""
    prompt: str = Field(min_length=1, max_length=2000)
    max_tokens: int = Field(default=64, ge=1, le=512)

class Usage(BaseModel):
    """How many tokens a call used (a token is a small piece of text the model reads or writes)."""
    prompt_tokens: int = Field(ge=0)
    completion_tokens: int = Field(ge=0)

    @computed_field
    @property
    def total(self) -> int:
        return self.prompt_tokens + self.completion_tokens

class ModelReply(BaseModel):
    """What a provider sends back. We check it before trusting it."""
    model: str = Field(min_length=1)
    text: str = Field(min_length=1)
    usage: Usage

ChatRequest holds the question we send, with a prompt of one to two thousand characters and a maximum token count between one and 512. Usage holds the two counts, and a computed field adds them up, so the total always agrees with its parts. ModelReply is what a provider sends back. Answer, Failure and FanOutResult are what we hand back to our own callers. These classes are tiny, but they carry a lot of safety: every border of our service has a description and a guard.

Where Does Validation Live?

Here is a question for you to try before reading on. Our service has several places where data changes hands: a request arriving from a user, a reply coming back from a model provider, a settings file read at start-up, and the results passed from one function to the next inside our own code. Where should validation live?

A good answer: put a customs desk at every border where data enters from outside, which means the incoming request, the provider's reply and the settings file. Inside the service, once an object has passed the desk, functions can trust its type, so they stay short and clean. One more border returns later in the course: data we read back from a database.

Async Python

Now we come to the idea behind the nine seconds versus three seconds from the start of the lesson. We begin with a waiter.

Waiting Is the Slow Part

Why does a model call take three seconds? Mostly because our program is waiting. It sends a request over the network, then waits while the provider's computer does the heavy work. That waiting is called I/O, short for input and output, and a program that spends most of its time waiting on I/O is called I/O-bound.

Picture a restaurant with three tables and one waiter. A synchronous waiter takes an order at table one, walks to the kitchen and stands there until the dish is ready, serves it, and only then visits table two. Three dishes of three minutes each mean nine minutes at the last table.

An asynchronous waiter takes the order at table one, hands it to the kitchen, and goes straight to table two, then table three. When a dish is ready, the waiter serves it. All three dishes cook at the same time, and the last table waits only three minutes. The waiter works at the same speed and simply keeps moving.

Python has this waiter built in, called the event loop, and it runs in a single thread. Our three tables are three model calls, and the kitchens are the providers' servers.

async and await

Now the words. A function declared with async def is a coroutine function. Calling it creates a coroutine, a recipe for work that the event loop can run. The word await marks a point where the function says: I am waiting for something, so event loop, please serve someone else, and resume me when my result is ready.

In our code, fetch_one sends a request with await client.post(...). At that moment the function pauses, and the event loop is free to start the next call. When the provider answers, the loop wakes the function at the very same line, with the response in hand.

Two rules keep you safe. First, await works inside an async function. Second, a call written without await only creates the coroutine, and Python prints a runtime warning that names it. To start a whole program, we call asyncio.run once, at the top.

Inside the Event Loop

Let's slow the event loop down and watch three tasks. The loop keeps a list of tasks that are ready to run and a list of tasks that are waiting. It picks one ready task and runs it until that task reaches an await.

Task one sends its request and reaches await, so it moves to the waiting list. Tasks two and three do the same. Now all three requests are travelling, and the loop rests. After three seconds, the replies arrive. Each reply moves its task back to the ready list, the loop resumes it right after its await, and the answer is stored. One thread, three tasks, and the only cost was a little bookkeeping.

This also shows what to avoid: a blocking call such as time.sleep holds the single thread, and every other task freezes. In an async program, waiting is always done with await.

gather: Start All, Wait for All

To run many coroutines together, we use asyncio.gather. Gather starts all of them, waits until every one has finished, and returns the results in the same order as the inputs. In our fan-out function, one line does it: gather over a generator that makes one fetch_one coroutine per provider.

Now the arithmetic, which you can repeat on a calculator. One after another, the waits add up: 3 + 3 + 3 = 9 seconds. All at once, the waits overlap, and the slowest call decides the total: max(3, 3, 3) = 3 seconds.

A note on words. This is concurrency: many tasks making progress during overlapping time, in one thread. Parallelism means several things running at the exact same instant on several processor cores. For I/O-bound work such as model calls, concurrency is the right tool.

Semaphore: The Door Host

What happens with a hundred providers, or a thousand requests? Starting everything at once can overload our own computer or run into a provider's rate limit, the number of requests a provider allows in a period. We need a limit on how many calls are in flight.

Our picture is a restaurant door host. Ten guests arrive, but the host lets only five inside at a time. The others wait at the door, and whenever a guest leaves, the host lets the next one in. In Python, this host is a semaphore, created with the number five.

A tiny example: ten calls of three seconds each, with a door that lets five in. The first five run together and finish at three seconds. The next five then run together and finish at six seconds. That makes two rounds, six seconds in total, compared with thirty seconds one by one.

Now, we'll look at how the semaphore sits in our code. We create it once in fan_out, and each call wraps its network request in async with:

sem = asyncio.Semaphore(max_concurrency)        # the door host: lets N in at a time
...
async def send() -> httpx.Response:
    ...
    async with sem:                                   # wait here when too many calls are in flight
        response = await client.post(
            f"{base_url}/v1/{provider}/chat",
            json=request.model_dump(),
            headers=headers,
            timeout=timeout_s,                        # never wait forever for one call
        )
    response.raise_for_status()                       # turn 4xx/5xx into an exception
    return response

Inside the block, the call holds one of the places, and when the block ends, the place returns to the host. Our tests measure the peak number of calls inside at once, and the peak stays at the limit.

Three Async Traps

  • Trap one: forgetting await. The coroutine is created and the work stays undone. Python warns you, so read the warning.
  • Trap two: blocking the loop. time.sleep, a heavy loop or a blocking library freezes the single thread. Use the async versions, such as asyncio.sleep and the async client from HTTPX.
  • Trap three: creating a new client for every call. A client keeps connections open and reuses them, like a taxi rank with cars waiting. Create one async client, share it among all tasks, and close it when you are done.

Reliable Clients

Real networks sometimes fail, so we teach our client to cope, and then we prove with tests that it does.

When Calls Go Wrong

What should our client do when a call goes wrong? Three kinds of trouble are common: a timeout, when the answer takes too long; a server error such as 503, which means try again later; and a rate limit, 429, which means too many requests.

Three rules cover most of what we need:

  1. Every call gets a timeout. A single stuck call could hold a place at the door forever. Our client gives every call ten seconds by default.
  2. Retry what is temporary. Timeouts, connection errors and the status codes 408, 429, 500, 502, 503 and 504 are worth another try. A 400, 401 or 404 will fail the same way next time, so those are reported at once.
  3. Stop after a few tries. Our policy allows three extra attempts. After that, the client returns a failure result for that provider, and the other providers still deliver their answers.

Backoff and Jitter

How long should we wait before trying again? Retrying immediately adds load to a server that is already struggling. A good habit is exponential backoff: wait one second, then two, then four, doubling each time, up to a cap of thirty seconds.

The doubling gives a struggling server room to recover. As a formula in plain text:

wait = min(cap, base × 2^attempt)

Here attempt counts from zero, base is the first wait and cap is the longest single wait. With base 1 and cap 30, the waits are 1, 2, 4, 8, 16 and then 30 seconds.

Now a problem. Imagine a thousand clients that all failed at the same moment. With exact doubling, all thousand retry after four seconds together, and the server receives a thousand requests in the same instant. This pile-up is called a thundering herd.

The cure is jitter, a random extra wait. We add a random amount between zero and half of the wait. After a four-second wait, each client adds between zero and two seconds, so the thousand requests spread over two seconds, roughly five hundred per second, instead of a thousand at once.

With a seed of 7, one possible run waits 1.16, 2.15 and 5.30 seconds. That is 8.61 seconds before the fourth try, compared with seven seconds for plain doubling. A little patience buys a calmer server.

Retries in Our Code

Now, we'll define the retry policy and the backoff function in reliability.py:

@dataclass(frozen=True)
class RetryPolicy:
    max_retries: int = 3      # extra attempts after the first one
    base_s: float = 1.0       # first wait, in seconds
    cap_s: float = 30.0       # the longest single wait
    jitter: float = 0.5       # random extra of up to this fraction of the wait

def backoff_delay(attempt: int, policy: RetryPolicy, rng: random.Random) -> float:
    wait = min(policy.cap_s, policy.base_s * 2**attempt)
    return wait + rng.uniform(0, wait * policy.jitter)

RetryPolicy collects the knobs in one frozen object, so one policy can be shared safely. backoff_delay is the formula above in code, plus the jitter. The helper call_with_retries runs the call and, for a temporary failure, logs a warning, computes the delay and sleeps. On the last attempt, or for a permanent failure, it raises the error.

In the real demo, a flaky provider fails twice with a 503 and then answers. To keep the demo short, we scale the base wait down to a quarter of a second:

$ uv run python demos/03_retries.py
asking the flaky provider (fails twice, then answers)

    91 ms  flaky: attempt 1 failed (HTTP 503); retrying in 0.29 s
   386 ms  flaky: attempt 2 failed (HTTP 503); retrying in 0.54 s
success after 0.86 s: [flaky] Prioritise the chest pain referral before the routine review.

Logging acts as the narrator of the program. Each retry leaves a clear line with the provider's name, the attempt number, the reason and the wait, so when something goes wrong in production, the story is already written.

The Double Charge

Retries bring a new danger, so let's tell a story. Our client asks a billing service to charge a patient's fee, once. The server charges the card, and then the reply gets lost on the way back. Our client reaches the timeout and sends the same request again. The server sees a request that looks brand new and charges the card a second time. The patient pays twice, and our retry logic caused it.

The fix is an idempotency key. Idempotent means that doing something twice has the same effect as doing it once. Before the first attempt, the client creates a random unique key and sends it in a header. The server remembers each key together with its reply.

Now replay the story. The first request carries key k, the server charges the card once and stores the reply under k. The reply gets lost, the client retries with the same key k, and the server answers: I already did this one, here is the saved reply. One charge, and the client still gets its answer.

The rule for our code: create the key once for each logical request, outside the retry loop, and send the same key on every attempt. Payment services such as Stripe accept an idempotency key header for exactly this reason.

Idempotency, Measured

Let's measure it with the mock billing provider, which counts every charge and loses its first reply. The client times out after half a second and retries:

$ uv run python demos/04_idempotency.py
The first reply is lost, so the client times out after 0.5 s and retries.
    log: billing: attempt 1 failed (ReadTimeout); retrying in 0.10 s
without an idempotency key: work done 2x, charged 2x  (client result: Answer)
    log: billing: attempt 1 failed (ReadTimeout); retrying in 0.10 s
with an idempotency key   : work done 1x, charged 1x  (client result: Answer)

Without a key, the ledger shows the work done twice and the card charged twice. With a key, the same story ends with work done once and one charge. The client received an answer both times, which is why this bug is easy to miss: the result looks fine, while the bill is wrong.

Now, we'll look at the top of fetch_one, where the key is created:

# One key per logical request, reused by every retry, so the server can spot repeats.
key = new_idempotency_key() if use_idempotency else None

async def send() -> httpx.Response:
    headers = {"Idempotency-Key": key} if key else {}
    ...

Because the key is made outside send, every retry reuses it.

Testing, Logging and Settings

pytest Basics

How do we know our reliable client really works, and keeps working next month? We write tests, small programs that check our code and run in seconds. The standard tool is pytest.

A pytest test is a function whose name starts with test. Inside it, we call our code and use assert, a statement that says this must be true. When every assert holds, the test passes; when one fails, pytest shows exactly which line and which values. Our lab has twenty-one tests.

pytest also offers fixtures, small helpers that prepare something the tests need. In our lab, one fixture tells the async tests to run on asyncio. And parametrize lets one test run with several inputs, which we use to check four different broken replies with a single test function.

Mocking the Network

How do we test network code while staying offline and free of charges? We replace the network with a mock. HTTPX has a built-in mock transport, so we give it a small function that plays the provider, and the client talks to our function instead of the internet. The fake provider answers instantly, so the tests are fast and free, and we can make it misbehave on purpose: return a 500, return an empty text, or fail twice and then succeed.

Now, we'll write a test that proves concurrency pays off. Each fake provider thinks for 0.2 seconds:

async def test_concurrent_is_faster_than_sequential() -> None:
    async def handler(request: httpx.Request) -> httpx.Response:
        await asyncio.sleep(0.2)                  # each provider "thinks" for 0.2 s
        return httpx.Response(200, json=reply(provider_of(request)))

    names = ["alpha", "beta", "gamma"]
    async with client_for(handler) as c:
        fast = await fan_out(BASE, names, REQUEST, client=c)
        slow = await fan_out_sequential(BASE, names, REQUEST, client=c)
    assert fast.wall_s < 0.45                     # about 0.2 s: all at once
    assert slow.wall_s >= 0.6                     # about 0.6 s: one after another

Three calls of two tenths of a second finish in under 0.45 seconds when concurrent, and take at least 0.6 seconds when sequential. A second test proves that with a limit of three, the peak number of calls in flight is exactly three, even with ten providers.

For retries we use a second trick. The sleep function is a parameter, so a test passes in a fake sleep that records the wait instead of waiting:

async def test_retries_then_succeeds_without_real_waiting() -> None:
    waits: list[float] = []

    async def fake_sleep(seconds: float) -> None:   # records the wait instead of waiting
        waits.append(seconds)

    ...
    policy = RetryPolicy(max_retries=3, base_s=1.0, jitter=0.0)
    assert await call_with_retries(flaky, policy, sleep=fake_sleep) == "ok"
    assert calls["n"] == 3 and waits == [1.0, 2.0]

The test checks that the waits were one second and two seconds, and the test itself takes a few milliseconds.

Testing Output That Varies

Model text changes from run to run, so how can a test compare it with an expected answer? Exact-match tests would fail at random. Three techniques solve this.

The contract. The first answer is to test what must always hold. Every answer has some text, a token count of seventeen and a source from our list of providers, and every provider is accounted for: answers plus failures equal the number of providers we asked.

The property check. Instead of one example, we try many random cases and check a rule. For jitter, two thousand random seeds each confirm that the delay lies between the wait and one and a half times the wait:

for seed in range(2000):
    rng = random.Random(seed)
    attempt = rng.randrange(0, 8)
    wait = min(30.0, 2**attempt)
    delay = backoff_delay(attempt, policy, rng)
    assert wait <= delay <= wait * 1.5

The snapshot test. We save the shape of a result in a file, and compare future runs with the file. We snapshot the structure, the sources and the token counts, and leave out the wording and the timing, which change.

Together, these three let us test systems whose exact words change, which is the situation with language models.

Logging, Settings and a Small CLI

Three small habits finish the foundation.

Logging. A log is the program's diary: each line has a time, a level such as info, warning or error, the name of the part that wrote it, and a message. We already saw our retry warnings. Use logging instead of print, because a setting can raise or lower the detail.

Settings. Our service reads its knobs from environment variables that start with CAREDESK_, using pydantic-settings: the base address, the maximum concurrency, the timeout, the retry limit and the backoff base. It is the customs desk again, this time for configuration. Now, we'll look at the class:

class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_prefix="CAREDESK_", env_file=".env", extra="ignore")

    base_url: str = "http://127.0.0.1:8765"
    max_concurrency: int = Field(default=5, ge=1, le=64)
    timeout_s: float = Field(default=10.0, gt=0)
    max_retries: int = Field(default=3, ge=0, le=8)
    backoff_base_s: float = Field(default=1.0, gt=0)
    backoff_cap_s: float = Field(default=30.0, gt=0)

If someone sets the maximum concurrency to the word zero, the program stops at start-up with a clear message instead of failing in a confusing way later:

pydantic_core._pydantic_core.ValidationError: 1 validation error for Settings
max_concurrency

A SQL Refresher

Many AI applications store their data in a relational database, and SQL is the language for asking questions. Later we build the app database and a text-to-SQL agent, so a quick refresher pays off.

Our Tables

A table is a grid: rows are records and columns are fields. Our lab has two tables of synthetic data. departments has an id and a name, and appointments has an id, a patient code such as SYN-0001, the department_id, a scheduled time and the wait in minutes.

The question for this refresher: which department keeps patients waiting the longest? We answer it in three steps: a join, a GROUP BY and a window function. We run the statements in SQLite, which ships with Python. They are standard SQL, and we use PostgreSQL for the app database later in the course.

JOIN: Connect Two Tables

A join connects the rows of two tables through a shared value. Appointments carry a department id, but people prefer names, so for each appointment we find the department whose id matches and put its name beside it. Picture two lists with a thread from each appointment to its department: appointments one to four lead to Emergency, and appointments five and six to Cardiology.

Now, we'll write the join:

SELECT a.id, d.name AS department, a.patient_code, a.wait_minutes
FROM appointments AS a
JOIN departments AS d ON d.id = a.department_id
WHERE a.id <= 6
ORDER BY a.id;

The result shows six rows. The first four are Emergency, with waits of 35, 50, 20 and 65 minutes, followed by two Cardiology rows.

GROUP BY: One Row per Group

A join keeps one row per appointment. A GROUP BY collapses rows that share a value into one row per group, and aggregate functions summarise each group: count, average and maximum.

SELECT d.name AS department,
       COUNT(*)                      AS appointments,
       ROUND(AVG(a.wait_minutes), 1) AS avg_wait,
       MAX(a.wait_minutes)           AS longest_wait
FROM appointments AS a
JOIN departments AS d ON d.id = a.department_id
GROUP BY d.name
ORDER BY avg_wait DESC;

Worked numbers, ready for a calculator. Emergency has four waits: 35, 50, 20 and 65. They add up to 170, and 170 / 4 = 42.5 minutes on average, with 65 the longest. Cardiology's three waits add up to 70, an average of 23.3. Radiology's five waits add up to 125, an average of 25.0. Sorted by average wait, Emergency comes first: it keeps patients waiting longest.

department | appointments | avg_wait | longest_wait
Emergency | 4 | 42.5 | 65
Radiology | 5 | 25.0 | 40
Cardiology | 3 | 23.3 | 30

Window Functions: Keep the Rows

A GROUP BY gives one row per department, but sometimes we want every row, plus something computed across a group of rows. That is the job of a window function: it keeps all the rows and adds a new column, calculated over a window of related rows.

We ask for two things in Radiology. First, a rank for each wait within the department, where 1 means the longest wait: PARTITION BY defines the group and ORDER BY decides the ranking. Second, a running average in time order:

SELECT d.name AS department, a.scheduled_for, a.wait_minutes,
       RANK() OVER (PARTITION BY a.department_id
                    ORDER BY a.wait_minutes DESC) AS wait_rank,
       ROUND(AVG(a.wait_minutes) OVER (
             PARTITION BY a.department_id
             ORDER BY a.scheduled_for
             ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW), 1) AS running_avg
FROM appointments AS a
JOIN departments AS d ON d.id = a.department_id
WHERE d.name = 'Radiology'
ORDER BY a.scheduled_for;

The waits 40, 30, 25, 20 and 10 receive ranks 1 to 5. For the running average, after the first appointment it is 40. After the second it is 25, because (40 + 10) / 2 = 25. After the third it is 23.3, and then 25 and 25:

department | scheduled_for | wait_minutes | wait_rank | running_avg
Radiology | 2026-03-02 08:15 | 40 | 1 | 40.0
Radiology | 2026-03-02 09:15 | 10 | 5 | 25.0
Radiology | 2026-03-02 10:15 | 20 | 4 | 23.3
Radiology | 2026-03-02 11:15 | 30 | 2 | 25.0
Radiology | 2026-03-02 12:15 | 25 | 3 | 25.0

Window functions power rankings, moving averages and comparisons of each row with the row before it, and they return when we build text-to-SQL agents.

Putting It All Together, and the Lab

A Tour of the Finished Code

Now we can see the whole program at work. Instead of a line-by-line reading, which the comments in the code on GitHub already provide, we tour the main moves.

The fan_out function creates the door host, a semaphore with the limit from our settings, opens one shared async client, and builds one fetch_one coroutine per provider. Then gather starts them all and waits. Inside fetch_one, the key is created once, and a send function wraps a single attempt: take a place at the door, post the request with a timeout, and raise an error for a bad status code. call_with_retries runs send and retries temporary failures with backoff and jitter.

When the reply arrives, model_validate_json is the customs desk. Good replies become answers, and any trouble, a timeout after all retries or a malformed reply, becomes a failure. fetch_one reports provider trouble as a result, so one bad provider leaves the others untouched, and a test proves it.

Lab: Twelve Calls

Here is a small challenge to try yourself. Suppose we ask twelve providers, each taking three seconds, and the door host lets four in at a time. How long will the whole fan-out take? Count the rounds, then the length of each round.

The answer: twelve calls with four places make 12 / 4 = 3 rounds. Each round takes three seconds, so the total is 3 × 3 = 9 seconds, compared with 36 seconds one by one. The file worked_examples.py prints this calculation too:

== 2b. Twelve calls of 3 s, door lets 4 in at a time
rounds: 3 (12 / 4)
each round takes 3 s -> total 9 s   versus one by one: 36 s
